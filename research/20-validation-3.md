# Validation 3: Windows shell, toolchain, deployment and test evidence

Adversarial cross-check, 2026-10-27. Each finding received a new search or direct read of different primary documentation, machine-readable release metadata, schema/API documentation, or runner configuration. Original sources were not treated as independent confirmation. No Windows build/run evidence was created; no app setup, settings changes, signing provisioning or GitHub writes occurred.

Dates are publication/update dates where visible; otherwise the source is explicitly undated and was accessed 2026-10-27. A product-owner recommendation establishes what the owner recommends, not a measured performance advantage. Separate Microsoft pages are independent documents but not independent publishers; where they disagree, this validation preserves the disagreement.

### F3.1 — .NET 10 LTS and current versions

- **Verdict:** CONFIRMED as of the research date.
- **Independent source:** Microsoft's [machine-readable .NET 10 release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/10.0/releases.json), fetched read-only 2026-10-27; release dated 2026-10-25. A fresh metadata query returned `latest-release=10.0.14`, `latest-runtime=10.0.14`, `latest-sdk=10.0.403`, `release-type=lts`, `support-phase=active`, `eol-date=2028-11-14`; the latest release lists SDKs 10.0.403 and 10.0.114. A separate search found [runtime version selection](https://learn.microsoft.com/en-us/dotnet/core/versions/selection), updated 2026-05-15.
- **Correction / contradiction:** None to the numeric claim. The machine-readable channel data supports the current lifecycle date over the earlier announcement's different date. SDK/runtime numbers are distinct. Self-contained runtime selection occurs at publish time; shipping a newer globally installed .NET runtime does not patch an existing bundled copy. Recheck before implementation and pin the selected SDK and servicing policy.
- **Source-quality flags:** Primary operational metadata and official deployment semantics, current, nonpromotional. This confirms availability/support metadata, not successful Far Flow compilation with that SDK.

### F3.2 — Windows App SDK 2.5.1 stable

- **Verdict:** CONFIRMED for highest stable package version; no implementation compatibility is established.
- **Independent source:** [NuGet flat-container version inventory](https://api.nuget.org/v3-flatcontainer/microsoft.windowsappsdk/index.json), fetched read-only 2026-10-27, independently filtered to non-prerelease semantic versions; highest entries were 2.1.3, 2.2.0, 2.3.1, 2.4.0 and **2.5.1**. Independent component check: [Microsoft.WindowsAppSDK.Runtime package inventory](https://www.nuget.org/packages/Microsoft.WindowsAppSDK.Runtime), last updated 2026-09-16, lists 2.5.1 and later 2.5.4-experimental.
- **Correction / contradiction:** The later 1.8 servicing package does not make 1.8 the numerically highest stable line. Experimental 2.5.4 is not stable. This does not independently prove every API/component in the metapackage shares that number or that the .NET 10 + inference dependency graph works. A separate NuGet registration endpoint did not yield parseable metadata during this check; date corroboration relies on the different Runtime package inventory, not a fabricated fetch result.
- **Source-quality flags:** Primary package registry, current. The separate registry endpoints share NuGet/backend ownership, so this is operational corroboration rather than independent publisher certification. Avoid relying on search snippets of a multi-release GitHub page: this search returned inconsistent heading/body combinations from that page.

### F3.3 — Recommended native UI framework

- **Verdict:** CONFIRMED as a Microsoft recommendation.
- **Independent source:** [Coming to Windows development](https://learn.microsoft.com/en-us/windows/apps/whats-new/coming-to-windows), live official migration guidance accessed 2026-10-27, explicitly recommends WinUI 3 for new Windows desktop apps. Fresh alternative-framework search also found the official [Windows developer FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq) confirming continued WPF support and modern Fluent theming; the FAQ is corroboration only because the dossier already cites its source file.
- **Correction / contradiction:** Do not turn the recommendation into a finding that WinUI is faster, smaller, easier to package or necessarily better for this waveform overlay than WPF. No comparative Far Flow measurements exist. The toolchain guide's one-command setup enables Developer Mode; that is not authorization to run it during planning. A WPF fallback remains technically credible; Avalonia's build-host portability does not remove native Windows integration work.
- **Source-quality flags:** Primary product documentation, current but promotional in framework positioning. High confidence in what Microsoft recommends; unmeasured task-specific superiority remains inference.

Independent OS policy check: [Windows 11 Home and Pro lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-11-home-and-pro), undated live lifecycle table accessed 2026-10-27; [supported Windows client versions](https://learn.microsoft.com/en-us/windows/release-health/supported-versions-windows-client), last updated 2026-09-29.
- **Correction / contradiction:** The runtime floor is not proof of app support or of .NET/native-inference compatibility on that floor. Edition/channel matters. Fresh lifecycle and release-health sources agree that 24H2 Home/Pro is no longer a current support target by 2026-10-27 and 25H2/26H2 remain candidates. However, the lifecycle page displays one-day differences from release-health servicing dates for several releases (for example 25H2's end date). Preserve the discrepancy if publishing exact dates; it does not change the present support conclusion. The 26H1 device-scoped branch and 26H2 build numbers must not be treated as simple monotonic version ordering.
- **Source-quality flags:** Official lifecycle/runtime sources, current. No Windows edition/build has been tested. A compatibility-floor claim and a product support matrix must remain separate.

### F3.5 — MSIX identity does not imply AppContainer

- **Verdict:** CONFIRMED, specifically for the normal full-trust desktop template configuration.
- **Independent source:** [How packaged desktop apps run](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes) and [Application manifest schema](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-f-application), undated current official references accessed 2026-10-27. Searches targeted `uap10:TrustLevel`, `mediumIL`, `appContainer`, and equivalent EntryPoint combinations.
- **Correction / contradiction:** Packaging and process trust are separate axes. The schema adds an important precision: **an omitted TrustLevel is not a universal medium-IL default**; it depends on activation attributes, and packagedClassicApp combinations can default to AppContainer. The desktop template's full-trust EntryPoint/runFullTrust configuration is what establishes medium IL. Full trust does not mean elevated administrator. The product must retain explicit manifest choices rather than infer privileges from an `.msix` extension.
- **Source-quality flags:** Primary schema and OS behavior references; stable contract despite undated pages. No installation under a standard account has been performed.

### F3.6 — Self-contained runtime closure and single-file claims

- **Verdict:** PARTIAL: the two-runtime requirement is confirmed; the optional single-file recipe remains an unresolved deployment claim.
- **Independent source:** [Official Windows AI sample deployment instructions](https://learn.microsoft.com/en-us/samples/microsoft/windowsappsdk-samples/windowsaisamples/), current sample page surfaced as published September 2026, explicitly sets both `WindowsAppSDKSelfContained=true` and `SelfContained=true`; [.NET publishing modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/), live official guidance accessed 2026-10-27; [.NET single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), updated 2026-03-25. Fresh searches targeted both properties, native library extraction and package-free execution.
- **Correction / contradiction:** “Fully self-contained” means neither .NET nor App SDK runtime prerequisites are assumed; it does not mean OS/native CRT/provider/model prerequisites vanish. The dossier correctly retained conflicting WinUI guides instead of resolving them by assertion. An additional conflict matters: the independent .NET guide calls `IncludeAllContentForSelfExtract` a **not-recommended .NET Core 3.1 compatibility mode that might be removed**, whereas the WinUI single-file recipe requires it. Therefore publish a folder/installer candidate and leave single-file uncommitted pending a pinned 2.5.1/.NET 10/native-worker clean-machine test. Self-extraction location, file paths, cold start and antivirus behavior are part of that test. The Windows AI sample is evidence for deployment properties only; its Copilot+/package-identity requirements do not apply automatically to the proposed ASR app.
- **Source-quality flags:** Primary sample and runtime documentation. The .NET single-file page is seven months old and contains older target examples; it is sufficient to reveal conflicting guidance, not prove .NET 10 WinUI behavior. No binary was built or installed.

### F3.7 — Capabilities and microphone/media access

- **Verdict:** CONFIRMED for declaration/app-model distinctions; deployment behavior remains unverified.
- **Independent source:** [uap7:Capability schema](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-uap7-capability), undated live official schema accessed 2026-10-27, enumerates globalMediaControl; [Microsoft's GSMTC console example](https://devblogs.microsoft.com/oldnewthing/20231108-00/?p=108980), published 2023-11-08. A fresh search specifically tried to disprove that GSMTC always needs MSIX/package identity.
- **Correction / contradiction:** The console sample is evidence against an unconditional “GSMTC is MSIX-only” rule; it does not prove every packaged/unpackaged trust configuration. The API is cooperative media-session control, not access to arbitrary sound. Keep microphone capability declarations, OS privacy denial and later revocation distinct. Do not advertise standard-user “input anywhere”: UIPI/elevated/secure-target restrictions persist even for a full-trust MSIX. The exact standard-user permission experience needs the real signed deployment form, not a development launch with preexisting grants.
- **Source-quality flags:** Primary schema and Microsoft engineering example. The example is older than six months, so it is counterevidence to a blanket restriction, not certification against the selected October 2026 toolchain. No API availability or permission matrix has been executed here.

### F3.8 — Desktop background lifecycle

- **Verdict:** CONFIRMED for ordinary full-trust desktop foreground/background behavior.
- **Independent source:** [Background task migration strategy](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/guides/background-task-migration-strategy), updated 2026-07-05; fresh independent search for WinUI suspension found its explicit statement that the UWP ApplicationTrigger suspension scenario does not occur for WinUI desktop apps. [Windows developer glossary](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-glossary), live official reference accessed 2026-10-27, separately states Win32 rather than UWP PLM behavior.
- **Correction / contradiction:** This does not promise uninterrupted execution through sleep, resource policy, process termination or every specially configured COM/background-task activation. No UWP `Suspending` event should be invented for the normal WinUI shell. Close-to-quit and worker termination remain product-owned behavior; keeping a hidden top-level window or owned job handle alive can defeat the desired exit semantics.
- **Source-quality flags:** Current official migration/API documentation. No material contradiction to the qualified claim; forum reports about special push/COM activation paths are weaker evidence and do not establish a normal-shell suspension rule.

### F3.9 — Signing is not a no-warning guarantee

- **Verdict:** CONFIRMED; signing-service eligibility is an additional missing gate.
- **Independent source:** [Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options), updated 2026-08-29, independently states OV/EV and Artifact Signing reputation accumulation rather than instant bypass. [Artifact Signing setup prerequisites](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart), updated 2026-05-21, independently describes publisher identity restrictions. Fresh search targeted “Artifact Signing individual European Union Spain eligibility” and EV reputation contradictions.
- **Correction / contradiction:** No valid signature guarantees first-download SmartScreen silence. Important omitted prerequisite: Public Trust individual developers must be in the **US or Canada**; organization eligibility includes the EU and other listed countries. A development session’s location does not establish the publisher’s legal entity or signing eligibility. Do not commit to Azure Artifact Signing until the actual publisher qualifies; retain an eligible CA/Store route. The free open-source signing route must not be assumed for this all-rights-reserved source-visible product. Store MSIX re-signing and Store MSI/EXE publisher-signing are different paths.
- **Source-quality flags:** Primary Microsoft service/signing documentation, current. The options page has commercial positioning/prices, but its trust/eligibility constraints are specific and checkable. The FAQ that merely links back to the dossier's SmartScreen page was not counted as independent confirmation.

### F3.10 — App Installer updates versus a standalone installer

- **Verdict:** PARTIAL: managed update checks are confirmed; prompt/block behavior needs narrower claims.
- **Independent source:** [UpdateSettings schema](https://learn.microsoft.com/en-us/uwp/schemas/appinstallerschema/element-update-settings), official API schema, last visible update 2024-05-07; [OnLaunch schema](https://learn.microsoft.com/en-us/uwp/schemas/appinstallerschema/element-onlaunch), updated 2025-02-06; [manual App Installer file construction](https://learn.microsoft.com/en-us/windows/msix/app-installer/how-to-create-appinstaller-file), live official guide accessed 2026-10-27. Fresh searches targeted launch/background update behavior and activation-blocking limitations.
- **Correction / contradiction:** The OS deployment service supports configured launch/background checks; a standalone EXE does not gain that simply by existing. But the OnLaunch remarks say ShowPrompt differs for UWP versus packaged desktop apps and that prompt/block attributes have launch-source limits, including desktop/taskbar shortcuts. These older specifics may conflict with newer generalized deployment prose. Preserve that conflict and test actual launch routes; do not promise a universal blocking/prompt flow for WinUI. Update activation cannot be relied on as a substitute for offline launch or explicit dictation-safe update deferral. Store, enterprise and third-party management are additional delivery channels, not necessarily an in-app updater.
- **Source-quality flags:** Primary schema rather than an aggregator, but older than six months and therefore suspect for detailed current UX. Stable element semantics support the core claim; exact current behavior remains a Windows test gate.

### F3.11 — ARM64/native dependency graph

- **Verdict:** CONFIRMED for a pure `win-arm64` process, with an ABI distinction added.
- **Independent source:** [Arm64EC interoperability](https://learn.microsoft.com/en-us/windows/arm/arm64ec), updated 2026-03-25, independently states an Arm64 process loads Arm64 binaries, while x64/Arm64EC processes can mix x64 and Arm64EC. A fresh search deliberately looked for the counterexample to “every native dependency must be rebuilt together.”
- **Correction / contradiction:** Plain Arm64, Arm64EC and Arm64X are not interchangeable labels. Arm64EC is a legitimate incremental native/emulated hybrid path, so a broad statement that *all* Arm-native strategies require every dependency to be pure Arm64 would be wrong. It does not invalidate the dossier's pure `win-arm64` release gate. For separate inference workers, dependency architecture must match each worker process, not necessarily the shell's architecture; IPC can cross that boundary. No .NET/ASR/provider ARM64EC compatibility is established. x64 emulation alone remains insufficient to advertise native ARM64 or equivalent inference speed.
- **Source-quality flags:** Primary ABI contract, seven-month-old update; unlike volatile release numbering, the architecture interoperability rule is a stable compatibility boundary. Still inspect the actual DLLs and run the chosen graph before support claims.

## What the researcher missed

- **Runner migration plans are not image contents.** Current manifest evidence contradicts the generic windows-2025/VS2026 assumption. Pin explicit labels and record actual OS/image/VS/.NET/native tool versions in build artifacts.
- **Signing eligibility is user-specific.** EU organizations can qualify for Artifact Signing Public Trust, while EU individuals are not listed as eligible. The user's legal publisher identity is unknown; a successful service choice cannot be promised before that is resolved.
- **Single-file has another documented risk.** The .NET recipe calls all-content self-extraction a compatibility mode that may be removed, whereas current WinUI guidance requires it. Keep the single-file shape out of release commitments until the pinned toolchain and native payload are tested.
- **Default trust is contextual.** Full-trust desktop template attributes establish medium IL; merely leaving TrustLevel out or adding package identity does not universally do so.
- **Updater UX is not uniform.** App-model and launch-route caveats in the schema can undermine a promised prompt/block/offline-launch flow. Test Start menu, desktop shortcut, taskbar and direct executable launches with network absent and with an update pending.
- **Native graph is per process.** A shell and isolated worker may use different architectures through IPC. Pure ARM64, ARM64EC hybrid and x64 emulation need honest separate labels; no support/performance claim follows from a UI framework architecture list.
- **“Self-contained” is not “everything local exists.”** Models, provider/CRT dependencies, extraction paths, explicit download policy, and updater network activity still require separate inventories and test gates. Do not accidentally import Copilot+/NPU/package requirements from optional Windows AI samples.
- **Standard-user testing must be clean.** Existing SDKs, trusted development certificates, preinstalled shared runtimes and prior privacy grants can hide broken release prerequisites. Testing must cover install, first offline launch, microphone denial/revocation, elevated-target fallback, upgrade/uninstall and worker exit without assuming developer-machine state.
- **Dates and product support must stay qualified.** Current official OS tables contain one-day lifecycle discrepancies and device-specific branches. Publish a chosen supported edition/build matrix backed by actual tests, not a broad “Windows 10+” conclusion from the SDK floor.
