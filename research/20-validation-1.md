### F1.5 — Conditional providers and CPU fallback

- **Verdict:** PARTIAL: the fallback/provider-placement warning is independently supported; the exact sherpa offline-TensorRT restriction remains supported only by the researcher's tagged source and was not independently confirmed.
- **Independent source:** https://onnxruntime.ai/docs/execution-providers/ — ORT provider architecture, living primary documentation retrieved 2026-10-27; nodes/subgraphs are assigned according to provider capability, with CPU following higher-priority providers. https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html — current ORT DirectML reference, retrieved 2026-10-27, publication date not exposed. https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html — primary CUDA requirements/configuration, current retrieval 2026-10-27.
- **Correction / contradiction:** Treat three separate questions as release gates: **was the requested EP initialized; which nodes actually ran there; did that exact model/precision produce correct and faster results?** A provider string or available-provider list answers none of the latter two. DirectML is now in sustained engineering, requires compatible DX12 hardware, and imposes session constraints: sequential execution, disabled memory-pattern optimization, and no simultaneous `Run` calls on one session. Its documented default adapter can be an iGPU on hybrid laptops. Missing these details makes “DirectML optional acceleration” incomplete.
- **Contradictory documentation to retain:** The dossier's Optimum citation says quantized CUDA models cannot run, but current ORT's own FAQ says CUDA supports `QuantizeLinear`, `DequantizeLinear`, and `MatMulInteger`: https://github.com/microsoft/onnxruntime/blob/main/docs/FAQ.md — primary current runtime documentation, retrieved 2026-10-27. This does **not** establish support for every signedness/operator combination. A recent upstream discussion identifies UINT8/INT8 constraints: https://github.com/microsoft/onnxruntime/discussions/26735 — first-hand developer discussion, 2025-12-05 to 2025-12-15, not a validated 2026 Windows benchmark. The independently inspected Parakeet conversion uses QUInt8 for the encoder and QInt8 for decoder/joiner. Do not claim either “int8 CUDA universally works” or “all quantized CUDA universally fails.”
- **Source-quality flags:** Primary ORT docs are current but internally uneven; wrapper-specific behavior cannot be inferred from ORT's general feature list. The researcher's tagged source is the strongest evidence for that wrapper's exact rejection branch; independent confirmation is absent. The lower-rung discussion is a test lead, not proof that the latest runtime still has the defect.
- **Searches that failed to independently establish offline TensorRT:** `site.k2-fsa.github.io/sherpa "TensorRT" "offline"`; `site.github.com/k2-fsa/sherpa-onnx "TensorRT" "only support"`. Results about the separate `sherpa`/Triton project do not validate `sherpa-onnx` Parakeet.

## What the researcher missed

- **Exact writer parity identity is material.** Add Qwen3-4B-Instruct-2507 explicitly; generic Qwen3-4B non-thinking mode is not the same model. No public Qwen-owned exact-checkpoint GGUF was established; evaluate a pinned community conversion or a reproducible owned conversion with license/notices and behavioral tests. Instruct-2507 is non-thinking-only; control the original hybrid family's mode separately if it remains a candidate.
- **DirectML is now a legacy/sustained-engineering route with operational constraints.** Session configuration, selected adapter, graph placement and dynamic-shape performance must be validated. Windows ML offers another EP-distribution layer, but its provider availability is not a proof of Parakeet correctness/performance, and on-demand EP downloads need explicit first-run/offline behavior. Official source: https://learn.microsoft.com/en-ie/windows/ai/new-windows-ml/supported-execution-providers — living Microsoft reference, retrieved 2026-10-27; differentiates included CPU/legacy DirectML from downloaded providers.
- **Quantized CUDA statements conflict across documentation.** The cited Optimum blanket limitation is not current enough to overrule ORT's own operator FAQ. Export precision, operator dtype/signedness, ORT build and actual profiler placement must be an exact matrix. In particular, this export quantizes the encoder differently from decoder/joiner.
- **Portable CPU binaries need an ISA policy.** Upstream release automation explicitly disables build-host native targeting and includes CPU variants. “x64” alone is not a CPU instruction baseline. Validate on the intended oldest supported Intel/AMD CPU and report unsupported-instruction errors clearly. https://github.com/ggml-org/whisper.cpp/issues/3889 (2026-06-18, upstream fixed build issue) is an additional fault lead about `GGML_NATIVE=OFF` and BMI2/variants.
- **Unicode and space-containing model paths are release gates.** A current open upstream issue reports Parakeet paths with `ö` being decoded incorrectly in a Windows executable: https://github.com/k2-fsa/sherpa-onnx/issues/3885, opened 2026-08-22 against v1.13.6 on Windows 11 25H2. This is not proof that v2.0.1 C# binding remains broken, but Dutch usernames, accented directories, relocated models and long paths should be in the clean-machine test matrix.
- **Artifact license follows its distribution/provenance.** Runtime licenses, model-source terms, converted-weight notices and NVIDIA NIM product terms must be recorded separately. The near-identical size of distinct Qwen GGUFs is a concrete counterexample to treating family name/size as identity.
- **Current model discovery may expose new native format routes.** The original evidence JSON itself lists an NVIDIA Parakeet v3 GGUF; the separate `transcribe.cpp` port documents multilingual native inference. This deserves a bounded evaluation if fallback choice remains open, but neither that port's performance reports nor another product's hardware benchmarks establish this ONNX pack's Windows behavior.
- **No empirical certification exists.** Keep CPU latency, mixed English/Dutch accuracy, post-quantization accuracy, short/no-speech hallucination behavior, dictionary/snippet interaction, writer fidelity, sustained memory, cancellation and concurrent ASR/writer VRAM fit as acceptance tests. No external benchmark can substitute for a pinned Far Flow build on the identified Windows CPU and RTX 3070-class machine.
