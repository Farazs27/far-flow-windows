## Findings

### F3.1 — Current stable LTS toolchain is .NET 10

- **Claim:** As of 2026-10-27, Microsoft's current support policy identifies .NET 10 as the actively supported LTS line, with current runtime patch 10.0.14 and SDK download 10.0.403.
- **Source:** https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core — official Microsoft support policy — updated 2026-10-25.
- **Source:** https://dotnet.microsoft.com/en-us/download/dotnet/10.0 — official Microsoft download inventory — latest release date 2026-10-25.
- **Source:** https://github.com/dotnet/core/blob/main/release-notes/10.0/10.0.14/10.0.14.md — upstream Microsoft release notes — release 2026-10-25; confirms SDKs 10.0.403 and 10.0.114 include runtime 10.0.14.
- **Confidence:** High.
- **Notes:** Current policy says .NET 10 support ends 2028-11-14 and .NET 8/9 support ends 2026-11-10. The older announcement at https://devblogs.microsoft.com/dotnet/announcing-dotnet-10/ (2025-11-11) says 2028-11-10 instead; retain this date discrepancy and prefer the current lifecycle table for planning. The SDK number and runtime number are different version axes. Self-contained apps carry their runtime and therefore need an app release to ship runtime servicing; installed shared-runtime automatic patch roll-forward is not a substitute for updating a bundled runtime.

### F3.3 — WinUI is Microsoft's new-app native default; alternatives remain viable

- **Claim:** Microsoft currently recommends WinUI 3 for new native Windows desktop UIs.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/winui/winui3/ — official Microsoft framework overview — updated 2026-10-02.
- **Confidence:** High for the recommendation; Medium for the following task-specific tradeoff assessment.
- **Notes — evidence and reasoned tradeoff, not a final selection:**
  - **C# + WinUI 3:** XAML/Fluent stock controls and Windows App SDK align directly with the requested Windows-native shell. It still needs Win32 interop for app-specific desktop behavior and an explicit deployment model. The current stable notes include a fix for `InputPointerSource.ActivationBehavior` not honoring `NoActivate`; a draggable waveform overlay must therefore pass a spike with the pinned runtime rather than rely on framework branding (F3.2 source, release 2026-09-16).
  - **WPF on .NET 10:** A Windows-only .NET UI framework with established XAML/data binding/graphics. Microsoft explicitly says it is supported, not deprecated, and that .NET 9+ includes a Fluent theme with light/dark and accent support. This weakens an “old-looking by definition” objection. Inference: it is a credible fallback if the overlay/accessibility/deployment spike fails, although the Windows integration still must be implemented. Sources: https://learn.microsoft.com/en-us/dotnet/desktop-wpf/overview/index — official overview, publication date not exposed; and https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/get-started/windows-developer-faq.md — official documentation source, `ms.date` 2026-05-28.
  - **Avalonia:** Its official Windows guide describes Win32 windowing/input/accessibility and Skia/Direct3D rendering with software fallback, and permits macOS/Linux cross-compilation. Inference: it could reduce shell build-host friction and offer cross-platform UI reuse, but it does not reuse the existing Swift/AppKit UI and is not the direct WinUI control stack. A Windows-only product gains less from its portability; native hotkey/audio/insertion integrations remain platform work. Source: https://docs.avaloniaui.net/docs/platform-specific-guides/windows/ — framework-owner documentation, publication/update date not exposed, retrieved 2026-10-27.

### F3.4 — Runtime compatibility floor is not a consumer support policy

- **Claim:** Windows App SDK's Windows 10 1809/build 17763 runtime floor does not establish that a Far Flow release is tested or supported on every Windows 10/11 edition and release.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/get-started/versioning-overview — official Microsoft versioning guidance — date not exposed in retrieved excerpt.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/support — official Microsoft SDK/Windows support matrix — updated 2026-09-24; explicitly conditions servicing on Windows edition/channel end dates.
- **Confidence:** High.
- **Notes:** The Windows SDK compile-time target is a separate axis: https://learn.microsoft.com/en-us/windows/apps/windows-sdk/ — official SDK overview, updated 2026-03-31 — advertises Windows SDK 10.0.28000 and lists 28000+/26100+ supported. The versioning overview still calls 26100 the current SDK in its FAQ; do not silently reconcile that stale example. Newer platform APIs need runtime guards when the application minimum is lower.
- **OS policy input:** https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information — official release-health inventory, updated 2026-10-26 — lists 26H2/build 26300 GA from 2026-09-29, 25H2/build 26200 still supported, 26H1/build 28000 scoped to new devices rather than an in-place update, and 24H2 Home/Pro at end of updates while Enterprise/Education differ. Initial validation can target 25H2 and 26H2 x64; this is a proposed gate, not tested coverage. https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro — official lifecycle page, publication date not exposed — gives normal Windows 10 Home/Pro EOS as 2025-10-14 and separately notes LTSC lifecycles. Windows 10 ESU/LTSC is therefore a separately scoped compatibility decision, not blanket support. .NET's supported-Windows page further conditions support on both OS and .NET lifecycle: https://learn.microsoft.com/en-us/dotnet/core/install/windows — official guidance, updated 2026-06-02.

### F3.5 — Default packaged WinUI desktop apps are full trust

- **Claim:** A default WinUI 3 MSIX desktop package runs at medium integrity/full trust rather than in the UWP AppContainer security model.
- **Source:** https://learn.microsoft.com/en-us/windows/msix/msix-container — official Microsoft packaging documentation — updated 2025-09-22; shows default `runFullTrust` and the separate steps for opting into AppContainer.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations — official capability documentation — updated 2026-10-02.
- **Confidence:** High.
- **Notes:** Package identity, package deployment, and AppContainer trust must be recorded separately. MSIX still changes installation paths, package identity and some storage/registry behavior; “full trust” is not administrator elevation. Inference: a user-level process can host native input/audio/inference integrations without assuming UWP restrictions or requesting admin by default. Exact API restrictions still need capability/API-specific checks.

### F3.6 — Fully self-contained WinUI deployment includes both runtimes

- **Claim:** A fully self-contained .NET WinUI app must include both .NET and Windows App SDK dependencies.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps — official Microsoft deployment guide — updated 2026-10-02.
- **Confidence:** High.
- **Notes:** Folder/xcopy/custom-installer deployment is documented with `WindowsAppSDKSelfContained=true` plus .NET self-contained publishing. Some optional SDK APIs retain additional MSIX service dependencies; check them individually. A no-admin per-user installer is feasible only when all payloads and registrations respect user scope: Inno Setup explicitly offers `PrivilegesRequired=lowest`, which does not request elevation (https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm — installer-owner documentation, undated). This is an installer capability, not proof of an unbuilt Far Flow installer. Native inference CRT/provider dependencies must be audited separately.
- **Contradictory single-file guidance:** The self-contained guide says native dependencies must remain separate and a WinUI single-file EXE cannot be produced. However, https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/deploy-overview and the dedicated https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app — official Microsoft guides, both updated 2026-10-02 — expressly support `PublishSingleFile` for unpackaged self-contained apps since App SDK 1.5. The dedicated guide says dependencies extract to a temp directory at first launch; this is not zero-extraction execution. It requires `WindowsPackageType=None`, `WindowsAppSDKSelfContained=true`, `SelfContained=true`, `EnableMsixTooling=true`, `IncludeAllContentForSelfExtract=true` and `PublishSingleFile=true`. https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/project-properties — official reference, updated 2026-10-02 — also documents a `WindowsAppSDKSingleFileVerifyConfiguration` build-validation target. Confidence is High that the documentation conflicts; actual single-file behavior with pinned 2.5.1 and native inference payloads remains unverified. A folder plus installer is supported without relying on that disputed shape.
- **Comparison input:** Framework-dependent unpackaged apps instead require installed runtime packages and bootstrap initialization: https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-unpackaged-apps — official guide, updated 2026-05-29. That runtime installer can fall back to current-user installation when machine-wide provisioning is unavailable; this disproves “unpackaged always needs admin,” while still leaving prerequisites to validate.
- **MSIX user-scope input:** https://learn.microsoft.com/en-us/windows/msix/msix-troubleshooting-guide — official guide, publication date not exposed — distinguishes `Add-AppxPackage` current-user installation from all-user provisioning. MSIX is therefore also a per-user candidate, conditional on a trusted signature, package contents and machine policy; installation of services or development certificate trust can require elevation. Validate the actual signed package under a clean standard-user account.

### F3.7 — Package capability declarations must follow the selected app model

- **Claim:** Package identity affects how microphone and global media-control access are declared and exposed to Windows privacy/capability handling.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations — official Microsoft capability reference — updated 2026-10-02.
- **Source:** https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager?view=winrt-28000 — official GSMTC API reference — publication/update date not exposed; API introduced in Windows 10 1809/build 17763; lists `globalMediaControl`.
- **Confidence:** High for documented declarations; Medium for untested unpackaged behavior.
- **Notes:** For an MSIX candidate, record `runFullTrust`, `microphone`, and `uap7:Capability Name="globalMediaControl"` as applicable manifest requirements. Microsoft recommends privacy-sensitive declarations even for medium-IL packages. Unpackaged Windows App SDK apps have no package manifest; device access uses OS-level permissions/consent instead (https://learn.microsoft.com/windows/uwp/devices-sensors/enable-device-capabilities — official device guidance, date not exposed). Desktop microphone privacy uses a desktop-app group control and cannot simply be described as the same per-app toggle flow as all Store apps (https://support.microsoft.com/en-us/windows/privacy/windows-camera-microphone-and-privacy — official support, undated). Handle access denial and later revocation. These documents do not prove that GSMTC always requires package identity in every full-trust desktop configuration; test `RequestAsync`, session enumeration and pause/resume in both candidate deployment forms before choosing identity as mandatory. GSMTC covers participating SMTC sessions, not every audio-producing process.

### F3.8 — WinUI desktop lifecycle does not automatically suspend like UWP

- **Claim:** A Windows App SDK desktop app keeps running when backgrounded rather than entering UWP process-lifecycle suspension.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/develop/launch/app-lifecycle — official Microsoft lifecycle guide — updated 2026-09-26.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/applifecycle/applifecycle — official Microsoft lifecycle overview — publication/update date not exposed in retrieved excerpt.
- **Confidence:** High.
- **Notes:** The guide also identifies Modern Standby/system sleep, Efficiency Mode throttling, shutdown/crashes and explicit/last-window exit as distinct concerns. Inference for Far Flow's close-to-quit requirement: a hidden waveform/auxiliary window or native worker must not accidentally preserve the process after the main close intent. Explicitly cancel capture/inference, release models, close all windows/workers and persist durable state; verify shutdown with process/resource evidence. Sleep/wake and device changes need their own integration tests rather than `Suspending`/`Resuming` assumptions.

### F3.9 — A valid signature does not guarantee immediate SmartScreen reputation

- **Claim:** Microsoft's current SmartScreen guidance says a newly signed release can still warn, including when an OV or EV certificate is used.
- **Source:** https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation — official Microsoft developer guidance — updated 2026-05-06.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/security — official Microsoft signing/security guidance — updated 2026-10-07; explicitly forbids committing signing keys/passwords or including certificate files in output.
- **Confidence:** High.
- **Notes:** Store distribution has a different signing/reputation path. Direct MSIX installs require a trusted package signature; self-signed trust must be installed on target machines (https://learn.microsoft.com/en-us/windows/msix/app-installer/installing-windows10-apps-web — official Microsoft App Installer guidance, undated in retrieved excerpt). Signing and no-admin installation are separate gates; do not offer user trust-store changes as the public no-admin solution.
- **Credential handling input:** The Azure-owned action recommends OIDC and currently runs on Windows x64 runners, not Windows Arm runners: https://github.com/Azure/artifact-signing-action/blob/main/README.md — upstream Microsoft signing-action documentation, undated current main. Its current example is `azure/artifact-signing-action@v2`, while a Microsoft Learn example still uses older `azure/trusted-signing-action@v0`; verify the chosen integration rather than copy the old snippet. Inference for a public repo: keep all signing certificate/PFX/private-key files and passwords out of tracked source and artifacts; use an external signing service/OIDC or protected release credentials only after approval/provisioning. No credentials or signing account have been created here.
- **Contradiction:** Avalonia's troubleshooting page claims EV/Trusted Signing immediate SmartScreen bypass (https://docs.avaloniaui.net/troubleshooting/platform-specific-issues/windows — framework-owner docs, undated, retrieved 2026-10-27). It conflicts with Microsoft's explicit statement that EV no longer bypasses SmartScreen; do not use that claim for release expectations.

### F3.10 — MSIX/App Installer and EXE installers have different update responsibilities

- **Claim:** An MSIX installed with App Installer can use Windows-managed update checks, whereas a standalone EXE/custom-installer distribution needs its own update mechanism or manual replacement flow.
- **Source:** https://learn.microsoft.com/en-gb/windows/msix/app-installer/auto-update-and-repair--overview — official Microsoft update documentation — displayed publication age approximately six months; exact publication date not exposed in retrieved excerpt.
- **Source:** https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/package-and-deploy/publish-first-app.md — official Microsoft documentation source — `ms.date` 2026-05-28.
- **Confidence:** High.
- **Notes:** Updates are delivery network operations, separate from offline inference. `.appinstaller` can control launch checks, prompts and activation blocking, and enterprise policy can override settings. The current guide says the `ms-appinstaller` web URI protocol is disabled by default; downloading/opening the file is a different route. Inference: choose and test explicit offline launch, update deferral during dictation, model/data persistence, interrupted install and rollback behavior for the selected delivery form; automatic updates are not implied by “MSIX file exists.” No host, updater or release feed has been provisioned.

### F3.11 — Architecture support requires matching native dependencies

- **Claim:** Shipping a native ARM64 build requires the complete native dependency graph to support ARM64; successful x64 emulation does not establish native ARM64 support.
- **Source:** https://learn.microsoft.com/en-us/windows/arm/add-arm-support — official Microsoft porting and testing guide — publication/update date not exposed in retrieved excerpt.
- **Source:** https://learn.microsoft.com/en-us/windows/arm/faq — official Microsoft platform FAQ — publication/update date not exposed in retrieved excerpt.
- **Confidence:** High.
- **Notes:** Microsoft calls for an ARM64 build configuration followed by native architecture tests on real Windows-on-Arm hardware or an ARM64 Windows VM. For this product, validate ASR/writing worker, BLAS/ONNX/provider/CRT DLLs, audio/interop bindings and installer payload architecture before advertising native ARM64. `win-x64` is an initial Intel/AMD build lane, not evidence that every x64 CPU supports every native engine instruction set. Official Native AOT desktop guidance warns that raising the instruction-set baseline raises the PC specification (https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/pc-dev/tutorials/get-started-with-custom-engine/native-aot-for-gaming?view=gdk-2604 — Microsoft GDK guide, publication date not exposed). Proposed validation gate: keep a general CPU fallback, publish actual required ISA/RAM/OS once the inference binaries are selected, and make RTX/NPU acceleration optional. No Far Flow minimum RAM, ISA or real-time speed is established by UI framework architecture support.

### F3.12 — Windows build automation and device certification are different evidence

- **Claim:** The present macOS research session has produced no Windows build/run or interactive/audio/GPU validation evidence.
- **Source:** Local read-only environment observation `uname -srm` → `Darwin 25.6.0 arm64` — primary session evidence — observed 2026-10-27; the brief confirms no established Windows toolchain or attached Windows test device.
- **Source:** https://learn.microsoft.com/en-us/windows/apps/get-started/start-here — official Microsoft WinUI build/run quickstart — updated 2026-10-14; uses .NET SDK 10 and Visual Studio 2026/WinUI workload, or currently public-preview winapp CLI 0.6+.
- **Confidence:** High.
- **Notes:** GitHub offers native Windows x64 labels (`windows-2025`, with VS 2026 after its June migration) and native Windows ARM64 labels (`windows-11-arm`/`windows-11-vs2026-arm`): https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job — official GitHub inventory, undated; https://github.blog/changelog/2026-05-14-github-actions-upcoming-image-migrations/ — official GitHub changelog, 2026-05-14. Those lanes can generate native build/package/test evidence once actually run, not retroactively certify the present plan. Pin runner image/toolchain details because `-latest` changes.
- **Validation boundary:** Standard runner specifications advertise VM CPU/RAM/architecture, not the user's physical microphone, keyboard firmware/Fn behavior, audio drivers, multi-DPI monitors or RTX 3070. Separate larger/GPU runners exist, but the official feature is plan/organization scoped and still does not establish the target MSI PC configuration: https://docs.github.com/en/actions/concepts/runners/larger-runners — official GitHub docs, undated. Do not claim all hosted CI UI tests impossible: Microsoft's own WinAppDriver CI guide supports interactive agents (https://github.com/microsoft/WinAppDriver/blob/master/Docs/CI_AzureDevOps.md — upstream Microsoft guide, undated historical VS2017/2019 examples). The appropriate claim is narrower: compile/unit/UI automation evidence must be labeled by its actual environment; real audio, input, insertion, accessibility, install/trust, sleep/wake and GPU benchmark acceptance still needs Windows execution evidence. Avalonia cross-compilation also cannot prove Windows runtime behavior (F3.3).

## Gaps — what I could not find

- A supplied Windows test PC, exact MSI model, CPU generation/ISA, RAM, RTX 3070 VRAM/driver configuration, microphone/headset, monitor/DPI arrangement, or installed Windows edition/build. The hardware class is not a measured configuration.
- A Far Flow Windows executable, a native build log, a package-install/uninstall result, a responsive real window, actual hotkey/cursor insertion proof, audio-device privacy/revocation proof, or CPU/GPU performance measurements. None were created as part of this planning task.
- Definitive official documentation that settles all GSMTC behavior for a full-trust unpackaged app without package identity. This remains a deployment-form spike, not a reason to promise or reject an installer route.
- A single consistent date/version story across all Microsoft pages: 1.8 servicing versus 2.x stable, Windows SDK “current 26100” example versus 28000 download overview, .NET 10 initial announcement EOS versus updated support table, contradictory WinUI single-file deployment instructions, and older signing-action snippets versus current upstream action. Exact sources above retain the discrepancies.
- A complete .NET 10 + App SDK 2.5.1 + chosen native inference dependency compatibility proof. Upstream framework architecture lists do not validate an unchosen native engine's ISA, runtime or provider requirements.
- A current official guarantee that a standard GitHub-hosted Windows VM provides physical audio capture, real keyboard/Fn behavior, GPU performance equivalent to RTX 3070, or the exact interactive desktop/integrity model needed by Far Flow. No blanket claim of hosted UI impossibility is made.
- An approved publisher identity, signing-service eligibility/account, certificate, Store account, update host/feed or production signing integration. No signing secrets or certificates belong in the planning-stage public repository.
- Installer implementation/license selection, per-user non-admin clean-machine proof, updater interruption/rollback behavior, MSIX storage-migration behavior, and persistence semantics across upgrades/uninstall. These require implementation and Windows tests.
- Quantified UI memory/startup/performance differences between WinUI 3, WPF and Avalonia for this specific app. Vendor framework guidance cannot supply those measurements.

## Disconfirming evidence check

- **Tried to break “WinUI is the only viable native choice.”** Official Microsoft FAQ confirms WPF remains supported and has a modern Fluent theme; Avalonia's own Windows guide permits macOS cross-compilation. These remain viable alternatives rather than being dismissed by age or build-host assumptions.
- **Tried to break “WinUI overlays just work.”** Current stable release notes include a NoActivate input behavior fix. The requested nonactivating movable waveform remains an explicit runtime/UI spike and acceptance test.
- **Tried to break “MSIX forces UWP sandbox or suspension.”** Official packaging and lifecycle documentation distinguishes medium-IL desktop packaging from AppContainer/UWP. The blanket restriction is false.
- **Tried to break “no-admin requires unpackaged” and “unpackaged requires admin.”** Microsoft documents per-user runtime install fallback, while Inno documents non-elevating install mode. Both routes are conditional on concrete payload/registration/signature decisions; neither slogan proves Far Flow install behavior.
- **Tried to break “WinUI single-file is impossible.”** The dedicated unpackaged-distribution guide and project-properties reference support a self-extracting single-file configuration, contradicting a sentence in the self-contained guide. The folder-installer candidate does not depend on this conflict; single-file must be verified with the actual pinned toolchain if selected.
- **Tried to break “signing guarantees no warnings.”** Current Microsoft SmartScreen documentation rejects that expectation, including EV, and contradicts Avalonia's troubleshooting advice.
- **Tried to break “CI can never test Windows UI.”** Upstream Microsoft examples do run UI tests in CI with an interactive agent. The remaining limit is the evidence actually obtained and the physical audio/input/GPU coverage, not a categorical ban on CI UI testing.
- **Tried to break “an x64 build on Arm proves Arm support.”** Microsoft's porting guide requires native dependencies and ARM64 execution/testing, independently of x64 emulation.
